Slice: #16 — Per-anchor GDELT DOC scalpel + BigQuery entity tags.

## Deferred (performance lens) — no overall per-night DOC-call ceiling

`run_anchor_scalpel` bounds DOC volume two ways: it is **gap-only** (skips interests the
BigQuery batch already covered) and **per-anchor capped**. In the normal case BigQuery
covers most interests, so the paced DOC loop fires only for a handful of long-tail gaps.

Pathological case: a **total BigQuery outage** yields an empty `covered_interest_ids`, so
EVERY active interest falls through to the paced DOC loop. At 1 req/5s that is
`sum(anchors) × 5s` of sequential work — potentially hours at 100× active interests. The
loop stays correct (sequential, resilient, never parallel) but can run long.

Not fixed now (Rule 2 — the ACs don't require it, and the gap-only skip bounds the normal
path). If the daily batch's wall-clock budget makes this a real risk, add a
`max_total_anchors` (or wall-clock) ceiling to `run_anchor_scalpel` that stops the loop
after N anchors and logs loudly. **Human/product call**: is a partial DOC night preferable
to a multi-hour one? File as a follow-up slice if yes.

## Minor (correctness) — outage log fires at 100% failure of even 1 anchor

`anchor_scalpel_doc_outage` (error level) fires when `anchors_failed == anchors_attempted`.
With a single attempted anchor that fails (a malformed anchor, not an outage) it still logs
"outage". Chosen deliberately: a 100% DOC failure rate is worth surfacing loudly (Rule 12);
the fix_suggestion hedges ("likely a penalty box or endpoint outage"). Accept as-is.
